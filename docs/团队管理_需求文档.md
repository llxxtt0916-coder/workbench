# 我的工作台 — 团队管理模块需求文档

> 版本：V1.1 | 日期：2026-07-20 | 定位：在"纯个人工作台"边界内新增"个人视角团队管理"能力
> 修订：V1.1 修订 status 存储/派生矛盾（B1），统一为"非 standalone 不落库、查询时实时派生"；同步修正 agencys 措辞、trainings 手动关联表述、时间字段口径。

---

## 一、模块定位与价值

### 1.1 模块定位

团队管理是"我的工作台"在**个人视角**下衍生出的管理能力：用户以管理者（项目负责人、带教老师、科室负责人等）身份，在工作台内**自建并维护**一份"团队人员花名册"，记录成员分工、培训考核与忙闲状态，并从成员维度聚合、跟踪、向上汇报工作进展。

### 1.2 核心边界（必须显式守住）

团队管理严格遵循"我的工作台"的纯个人工具定位，**不自相矛盾、不越红线**：

| 边界 | 说明 |
|------|------|
| 成员是"记录对象"，不是"使用者" | 成员不登录、不协作、不共享；全部数据由用户一人录入、查看 |
| 数据不跨人同步 | 团队成员数据仅存于用户本地工作台，不做实时同步、不共享给其他账号 |
| 不做多人协作 | 无评论、无指派接收、无成员自填入口 |
| 与外部机构对接人解耦 | 外部机构对接人继续走现有 `agencys` 模块；本模块只管**内部人** |
| 与"个人任务"同一份底座 | 成员任务仍承载于 `todos`，仅以 `category:['团队']` 打标，不新增 owner 字段 |

> 一句话：**团队管理 = 用户脑中那张"谁在负责什么"的台账，被结构化、可聚合、可导出。** 它是用户的助手视角，不是成员的工作台。

### 1.3 价值主张

| 用户痛点 | 模块解法 |
|----------|----------|
| 成员分工记在脑子/微信里，交办后无追踪 | 人员花名册 + 委派追踪枢纽，谁负责什么一目了然 |
| 会议行动项、培训学员散落各处，无法按人聚合 | 通过 `TeamAssignment` 只读 join 既有会议/培训数据，按人汇总 |
| 向上汇报缺少"团队维度"数据支撑 | 团队任务视图 + 团队汇总（驾驶舱团队维度） |
| 成员培训散落、证书易过期 | 培训考核关联（学员维度培训台账 + 证书到期提醒） |
| 不知道谁忙谁闲、谁快爆了 | 轻量忙闲看板（基于委派负载派生，可选手动标记） |
| 成员信息随人员调走而丢失 | 软删除保留，历史/调走成员不物理删 |

## 二、用户画像（多重身份）

用户身份是**多重**的，本模块不得锚定在"疾控监督员"单一身份。以下画像共享同一套"成员 = 记录对象"的模型。

### 2.1 项目负责人

| 维度 | 描述 |
|------|------|
| 典型工作 | 接上级任务 → 拆解 → 委派给组内成员 → 跟踪进度 → 向上汇报 |
| 高频痛点 | 成员多、任务杂，手写分工表易漏；交办后没人跟踪，临期才发现没动 |
| 模块诉求 | 人员花名册 + 委派追踪 + 成员视图（按人看任务）+ 团队汇总 |

### 2.2 带教老师 / 导师

| 维度 | 描述 |
|------|------|
| 典型工作 | 安排学员培训、跟培训考核、积累评价、出科鉴定 |
| 高频痛点 | 学员培训记录散落，证书过期遗忘；评价主观、无积累 |
| 模块诉求 | 培训考核关联（学员维度培训台账）+ 考核卡 `TeamMetric`(P2) + 花名册 tags 区分"学员/已出科" |

### 2.3 科室 / 团队负责人

| 维度 | 描述 |
|------|------|
| 典型工作 | 统筹科室日常、看谁忙谁闲、调配人力、做月度团队小结 |
| 高频痛点 | 凭感觉判断忙闲，临期才发现某人手里压了一堆活 |
| 模块诉求 | 轻量忙闲看板（委派负载派生）+ 团队汇总 + 导出 |

### 2.4 会议组织者

| 维度 | 描述 |
|------|------|
| 典型工作 | 组织会议、分派行动项、会后盯闭环 |
| 高频痛点 | 行动项 assignee 是自由文本，换人/同名易混乱；无法按人看"他还欠我几个行动项" |
| 模块诉求 | 成员选择器联想选人 + `TeamAssignment(sourceType:'meetingAction')` 闭环追踪 |

> 设计约束：同一用户可同时是上述多种身份；通过 `TeamMember.group` / `tags` 过滤，**多重身份切换不混圈子**。

### 3.1 在现有架构中的位置

团队管理作为独立模块接入，与现有"工作记录"统一底座保持**只读 join**关系，不侵入 `todos` 结构：

### 3.2 导航与入口

| 入口 | 位置 | 说明 |
|------|------|------|
| 团队管理主菜单 | 侧边栏新增"团队" | 花名册 + 委派追踪 + 团队汇总 + 忙闲看板 |
| 成员选择器 | 全局组件 | 在会议行动项、独立委派、培训关联处触发，输入即联想 |
| 成员视图 tab | 待办工作页内新增 tab | 选择成员后，过滤展示"该成员的任务"（只读 join） |
| 驾驶舱团队维度 | 驾驶舱下钻 | 团队任务完成率/逾期率统计（向上汇报数据） |

### 3.3 关键设计原则

1. **花名册是"人名词典地基"**：`TeamMember.name` 作为 join key，让 `meetings/trainings` 中的自由字符串可字典化匹配。
2. **成员任务零侵入**：`todos` 不新增 owner 字段；成员视图仅通过 `TeamAssignment` 关联过滤。
3. **只读 join 既有数据**：委派追踪不复制任务内容，只建立"成员 ↔ 既有任务"的索引关系；非 standalone 来源的 `status` 不作为独立字段落库，查询时实时派生。
4. **忙闲是派生量**：基于委派负载（待办/逾期数）计算"忙/闲"，可选叠加手动标记。

## 四、数据模型

### 4.1 设计约束（不可改动）

- **`todos` 零改动**：不新增 `owner` 等任何字段；团队任务仅以 `category:['团队']` 打标。
- **字段命名规范**：`content` = 主体内容，`note` = 补充备注；`name` = 台账/人员类，`title` = 灵感类。
- **软删除**：删除统一标记 `deleted: true`，不物理删除（历史/调走成员保留）。
- **既有实体零改动**：`meetings.attendees[]`/`actionItems[].assignee` 与 `trainings.organizer` 保持自由字符串，可选补 `assigneeMemberId`（非必填）。

### 4.2 新增实体：TeamMember（人员花名册，与 inspirations/trainings 同级）

```typescript
interface TeamMember {
  id: number;          // 主键
  name: string;        // 姓名 —— join key：让 meetings/trainings 字符串可字典化匹配
  role?: string;       // 角色 / 岗位（如：主管、学员、联络员）
  group?: string;      // 圈子分组（如：项目A / 科室B / 带教C）
  contact?: string;    // 联系方式（最小化收集，建议仅必要项）
  note?: string;       // 补充备注
  tags?: string[];     // 多标签（多重身份过滤，如：['学员','已出科','核心']）
  deleted?: boolean;   // 软删除（调走/历史成员保留）
}
```

### 4.3 新增实体：TeamAssignment（委派追踪枢纽，替代"给 todos 加 owner 字段"）

```typescript
interface TeamAssignment {
  id: number;
  memberId: number;    // → TeamMember.id
  sourceType: 'meetingAction' | 'training' | 'todo' | 'standalone';
  sourceRef: number;   // 指向具体来源：
                       //   meetingAction → meetings.id（行动项由 member.name 匹配 assignee / 或 assigneeMemberId 定位）
                       //   training      → trainings.id
                       //   todo          → todos.id
                       //   standalone    → 0（独立委派，自带状态）
  status?: '进行中' | '已完成' | '已逾期' | '已取消';  // 仅 standalone 来源写入；
                                                       // todo/meetingAction/training 来源在查询时由被引用实体
                                                       // 实时派生，DB 不存储该值
  deadline?: string;   // 仅 standalone 自带；其他来源读被引用实体的 deadline
  note?: string;       // 委派补充说明
  createdAt: string;   // 创建时间（YYYY-MM-DD）
  deleted?: boolean;   // 软删除
}
```

**status 统一规则（全文档遵循）：**

- `sourceType` 为 `todo` / `meetingAction` / `training` 时：`status` **不落库**，查询时实时由被引用实体派生（todo 读 `todos.status`；meetingAction 读 `actionItems[].done`；training 读 `trainings.status`）。被引用实体状态是唯一真相源，`TeamAssignment` 不写入、不回写、不同步该值。
- `sourceType` 为 `standalone` 时：`status` 由本记录自带并持久化到 DB。

**sourceRef 解析语义（按 sourceType）：**

| sourceType | sourceRef 含义 | 状态/截止来源 |
|------------|----------------|---------------|
| `todo` | `todos.id` | 读 `todos.status` / `todos.deadline`（实时派生，DB 不存 status） |
| `meetingAction` | `meetings.id`，行动项由 `member.name` 匹配 `actionItems[].assignee`（若补 `assigneeMemberId` 则按 id 精确定位） | 读 `actionItems[].done` / `actionItems[].deadline`（实时派生，DB 不存 status） |
| `training` | `trainings.id`（参训成员由 `TeamAssignment(sourceType:'training')` **手动关联建立**，用户逐人建派） | 读 `trainings.status` / `trainings.endDate`（实时派生，DB 不存 status） |
| `standalone` | `0`（独立记录） | 读本记录 `status` / `deadline`（status 落库） |

### 4.4 新增实体：TeamMetric（考核卡，P2）

```typescript
interface TeamMetric {
  id: number;
  memberId: number;    // → TeamMember.id
  period: string;      // 考核周期（如：2026-Q2 / 2026上半年）
  dimensions?: { name: string; score?: number }[];  // 多维评价
  events?: string[];   // 关键事件（如：出科、获奖、失误）
  note?: string;       // 考核说明
  createdAt?: string;  // 创建时间（YYYY-MM-DD）
}
```

### 4.5 既有实体零改动（仅可选增强，非必填）

```typescript
// meetings：actionItems[].assignee 保持字符串，可选补——
interface ActionItem {
  text: string;
  assignee?: string;        // 保持自由字符串（兼容历史数据）
  assigneeMemberId?: number;// 可选：精确定位到 TeamMember（非必填）
  deadline?: string;
  done: boolean;
}

// trainings：organizer 保持字符串；参训成员由 TeamAssignment(sourceType:'training') 手动关联建立（用户逐人建派）

// todos：不新增任何字段；团队任务仅 category:['团队']
```

### 4.6 与统一底座的兼容关系

```
工作记录 (todos) ── 统一底座（零改动）
  │
  └─ category:['团队'] 打标（团队任务）

TeamMember ─── 独立实体（新增）
  │ 1
  │ N
TeamAssignment ─── 委派追踪枢纽（新增，只读 join 既有实体）
  ├─ (N:1) → todos      (sourceType:'todo',      sourceRef=todos.id)
  ├─ (N:1) → meetings   (sourceType:'meetingAction', sourceRef=meetings.id)
  ├─ (N:1) → trainings  (sourceType:'training',  sourceRef=trainings.id)
  └─ (N:1) → 独立委派    (sourceType:'standalone', status/deadline 自带并落库)

TeamMetric ─── 考核卡（新增，P2，独立实体）
```

## 五、核心用户旅程（≥5 场景，覆盖多重身份）

### 旅程 1：项目负责人跟分工（todos + TeamAssignment.sourceType:'todo'）

```
接到上级任务 → 在工作台新增待办（category 勾选"团队"）→ 打开"委派"面板
  → 成员选择器输入"张" → 联想选中 张XX → 建立 TeamAssignment(todo)
  → 待办按成员聚合到"成员视图"tab
  → 日常点开成员视图，看张XX 还有几项进行中、有无逾期
  → 到期前提醒 → 完成后待办标记完成 → TeamAssignment 状态自动派生展示为完成（DB 不存储）
```

### 旅程 2：带教老师跟培训考核（TeamAssignment.sourceType:'training' + TeamMetric P2）

```
培训模块新增"XX 业务培训" → 在培训关联处选参训成员（成员选择器，逐人建派）
  → 建立 TeamAssignment(training, sourceRef=trainings.id)
  → 培训结束、证书下发 → 系统按 certificateExpiry 提醒防过期
  → 出科时（P2）填写 TeamMetric（维度评分 + 关键事件）
  → 花名册 tags 标记"已出科"，便于后续过滤
```

### 旅程 3：科室负责人看忙闲（忙闲看板）

```
打开团队管理 → 忙闲看板
  → 系统基于 TeamAssignment 负载派生：某成员"进行中/待办"数高 → 标"忙"；接近 0 → 标"闲"
  → 逾期项额外高亮（潜在爆雷）
  → 可选：手动把某成员标记"忙/闲"（如休假）
  → 据此调配人力，避免忙的更忙
```

### 旅程 4：会议组织者跟行动项闭环（meetings 字符串 + resolveMember + TeamAssignment）

```
会议模块新增会议 → 填写 actionItems（assignee 填"李XX"自由文本）
  → 系统 resolveMember("李XX") 匹配花名册 → 建议补 assigneeMemberId（非强制）
  → 一键"生成委派" → 建立 TeamAssignment(meetingAction, sourceRef=meetings.id)
  → 会后盯闭环：成员视图/委派追踪里看李XX 欠几个行动项、是否逾期
  → 行动项 done=true → 委派状态自动派生展示为完成（DB 不存储）；逾期自动标红
```

### 旅程 5：考核负责人积累评价（TeamMetric，P2）

```
出科 / 季度末 → 打开成员花名册 → 选成员 → 新建考核卡
  → 填维度评分（业务能力/协作/出勤） + 关键事件 + 备注
  → 可跨周期对比，支撑向上汇报与人才判断
```

### 旅程 6：多重身份切换不混圈子（group / tags 过滤）

```
用户既是"项目负责人"又是"带教老师"
  → 花名册给成员打 group（项目A / 带教C）与 tags
  → 委派、汇总、忙闲均支持按 group/tags 过滤
  → 切到"带教"视角只看学员，切到"项目"视角只看项目成员，互不串
```

## 六、功能范围（In-Scope / Out-Scope）

### 6.1 In-Scope

1. **人员花名册**：增删改查、标签、分组、软删除、备注、联系方式。
2. **成员选择器**：输入即联想选人（基于 `TeamMember.name`），用于会议行动项、独立委派、培训关联。
3. **委派追踪（TeamAssignment）**：建立"成员 ↔ 任务"索引，跟踪进度、逾期、查时派生状态。
4. **团队任务视图（成员视图 tab）**：在待办内按成员过滤展示其任务（只读 join，零侵入）。
5. **会议 / 培训行动项打通**：通过 `TeamAssignment` 关联 `meetings`/`trainings`。
6. **培训考核关联**：学员维度培训台账 + 证书到期提醒；考核卡 `TeamMetric`（P2）。
7. **轻量忙闲看板**：基于委派负载派生"忙/闲"，可选手动标记。
8. **团队汇总**：按成员聚合完成率、逾期率、负载（驾驶舱团队维度）。
9. **成员提醒**：委派临期 / 逾期提醒（复用现有提醒机制）。
10. **导出**：花名册、成员任务、团队汇总导出。

### 6.2 Out-Scope（红线，显式列出）

| 红线 | 原因 |
|------|------|
| **多人协作 / 团队共享** | 纯个人工具定位；成员是记录对象不是使用者 |
| **成员账号 / 登录** | 成员不登录、不协作 |
| **成员自填入口** | 全部数据由用户录入 |
| **权限 / 审批** | 无外部用户，审批在线下完成 |
| **实时同步 / 跨人共享** | 数据不跨设备/跨人同步（Gitee 仅作个人备份） |
| **邀请加入** | 没有"成员账号"概念 |
| **跨人消息 / 即时通讯** | 非沟通工具 |
| **外部机构对接人** | 继续走现有 `agencys` 模块 |
| **详细去向（在岗/出差/请假地点状态）** | 仅做轻量忙闲，不做地点状态记录 |

## 七、功能优先级矩阵（RICE）

> RICE 得分 = (Reach × Impact × Confidence) / Effort，沿用 PRODUCT_DESIGN.md 框架。

| 1 | 人员花名册 + 成员选择器（人名词典地基） | 10 | 9 | 9 | 3 | 270 | 🔴 P0 |

### 驱动指标（L1）

| 指标 | 基线 | 目标（3 个月） | 数据来源 |

| 忙闲看板覆盖成员数 | 需测算 | ≥ 80% 在册成员有负载数据 | TeamAssignment |

## 十、非功能性需求

### 10.1 本地存储

- 团队管理数据随现有 `data.json` 一并存于 `localStorage`，由统一的 `DataStore` 抽象层持久化。
- 新增集合 `teamMembers`、`teamAssignments`、`teamMetrics`，与 `todos`/`meetings`/`trainings` 同级。
- 复用现有 Gitee 同步机制做**个人跨设备备份**（注意：是用户个人备份，不是跨人共享）。
- `repairData()` 需覆盖新增实体的字段补全与软删除兼容。
- **status 落库约束**：仅 `TeamAssignment(sourceType:'standalone')` 的 `status` 持久化；其余来源的 `status` 查询时实时派生，不写入 DB。

### 10.2 隐私（他人信息的去标识化与最小化收集）

> 成员是"他人信息"，需遵循最小化与去标识化原则。

- **最小化收集**：`TeamMember` 仅收集必要的 name / role / group；`contact` 为可选，建议只存工作联系方式，不强制手机号等敏感字段。
- **去标识化建议**：对外导出/汇报时，提供"隐去联系方式"选项；团队汇总默认不展示 `contact`。
- **本地优先**：数据不离开用户设备，不上传任何服务端，不与成员本人互通。
- **软删除即合规**：调走成员标记 `deleted:true`，既保留历史关联（汇总不丢数据），又可在视图中默认隐藏。
- **导出安全**：导出文件含他人信息，提示用户"仅限个人工作用途，勿外发敏感字段"。

### 10.3 移动端

- 沿用现有 PWA（manifest 已补全），移动端浏览器可访问。
- 忙闲看板、成员视图、委派列表需在窄屏下可滚动、可点选；成员选择器在移动端支持触屏联想。
- 移动端优先满足"查看"与"快速标记完成"，录入以桌面端为主。

## 十一、验收标准（可测试）

### 11.1 花名册与成员选择器

- [ ] 可新增/编辑/软删除（非物理删）成员，字段含 name/role/group/contact/note/tags。
- [ ] 软删除后，花名册列表默认不显示该成员，但 TeamAssignment 历史关联仍可追溯。
- [ ] 成员选择器在输入时按 `name` 模糊联想，选人后回填；历史数据无对应成员时可手填并提示"加入花名册"。

### 11.2 委派追踪

- [ ] 对一条 `todos`（category 含"团队"）可建立 TeamAssignment(todo)，成员视图按该成员过滤出此任务。
- [ ] `todos` 状态变为"已完成"时，对应 TeamAssignment 状态**自动派生展示为"已完成"**（DB 不存储该值，查询时实时计算）。
- [ ] `todos.deadline` 过期未完成，TeamAssignment 派生展示"已逾期"且高亮。
- [ ] standalone 委派可自带 status / deadline 并落库，不依赖被引用实体。
- [ ] 建立委派不改变 `todos` 任何字段（零侵入校验）。
- [ ] 校验 DB：非 standalone 来源的 TeamAssignment 记录中不存在持久化的 `status` 字段值。

### 11.3 跨模块打通

- [ ] 会议 actionItems 中 assignee 为自由文本时，resolveMember 能按 name 匹配花名册并建议补 assigneeMemberId。
- [ ] 会议"生成委派"后，TeamAssignment(meetingAction) 建立；行动项 done=true 时，委派状态**自动派生展示为完成**（DB 不存储该值）。
- [ ] 培训关联参训成员（用户逐人建派）后，TeamAssignment(training) 建立，可于成员维度查看其培训。

### 11.4 忙闲看板

- [ ] 忙闲由"该成员进行中/待办委派数"派生：高于阈值标"忙"，接近 0 标"闲"。
- [ ] 支持手动覆盖标记"忙/闲"，手动标记优先级高于派生值。
- [ ] 逾期项在忙闲看板额外高亮提示。

### 11.5 团队汇总与导出

- [ ] 团队汇总按成员聚合完成率、逾期率、负载，数据来源为 TeamAssignment join。
- [ ] 驾驶舱团队维度可下钻到成员明细。
- [ ] 支持导出花名册、成员任务、团队汇总（导出时可选隐去 contact）。

### 11.6 兼容性与回归

- [ ] `todos` / `meetings` / `trainings` 既有字段与数据结构零改动（除可选 `assigneeMemberId`）。
- [ ] 既有数据（含历史 meetings/trainings）升级后不丢、不报错。
- [ ] 所有时间字段沿用 `YYYY-MM-DD` 规范；新增实体的删除均为软删除；非 standalone 的 `status` 不入 DB。

## 十二、风险与开放问题

### 12.1 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 自由字符串匹配歧义（同名成员、别名） | resolveMember 匹配错人 | 提供可选 `assigneeMemberId` 精确定位；匹配时提示确认 |
| 委派状态失真 | 进度展示错误 | 非 standalone 来源的 `status` 一律查询时由被引用实体实时派生，DB 不存储；被引用实体状态为唯一真相源，TeamAssignment 不写入、不回写、不同步 |
| 忙闲阈值主观 | "忙/闲"误判 | 阈值可配置；手动标记可覆盖 |
| 隐私合规（他人信息本地存储） | 个人工具边界模糊 | 最小化收集 + 导出脱敏提示 + 软删除保留 |
| 与现有提醒机制耦合 | 提醒逻辑复杂化 | 委派提醒复用现有 deadline 提醒，不新建通道 |

### 12.2 开放问题（需用户后续拍板）

1. **actionItems 精确引用**：`meetingAction` 的 sourceRef 指向 `meetings.id`，但会议可能含多条行动项。当一次会议中同一成员有多条行动项、或需逐条追踪时，是否需要给 `ActionItem` 增加稳定 `id`（而非仅靠 assignee 文本匹配）？—— 当前方案按 `member.name` 匹配整场会议行动项，粒度到"会议级"；如需"行动项级"追踪需补充 id。
2. **忙闲阈值**："忙"的派生阈值（如进行中≥N 项）具体数值与是否可配置，待用户定。
3. **成员选择器是否可"一键建成员"**：输入不存在的人名时，是仅提示"加入花名册"还是允许弹窗快速新建？交互细节待定。
4. **TeamMetric 评分维度**：P2 考核卡的默认维度（业务能力/协作/出勤等）与评分量表（5 分制 / 百分制）待用户定。
5. **导出格式**：导出优先 CSV 还是含排版的 HTML/Markdown？是否需与月报模板对齐？
6. **`agencys` 边界对齐**：本模块只管内部人，外部机构对接人走 `agencys`；`agencys` 已在基座中存在，需确认其字段结构以便与团队管理边界对齐，避免术语与实现偏差。
